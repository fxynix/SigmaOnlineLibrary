# «Парное программирование»

## Введение

В рамках лабораторной работы было реализовано два компонента онлайн-библиотеки: функциональность управления книгами и система отзывов. Работа выполнялась с использованием методологии парного программирования в соответствии с техническим заданием.

---

## 1. Какие стили парного программирования использовались

В процессе разработки были опробованы два стиля:

1. Ведущий-ведомый 

   Один разработчик (более опытный в Spring Boot) выступал в роли наставника, направляя процесс и объясняя архитектурные решения (настройка JPA-связей, оптимизация запросов через @NamedEntityGraph). 
   Второй разработчик непосредственно писал код, осваивая новые технологии (JPA-репозитории, DTO-мапперы).
   Стиль использовался на начальном этапе при создании моделей данных и настройке связей между сущностями.

2. Пинг-понг

   Один разработчик писал тест (unit-тест для сервиса или контроллера).
   Второй разработчик писал реализацию, проходящую этот тест.
   Стиль активно применялся при разработке бизнес-логики расчета рейтинга книг и валидации отзывов.

## 2. Какую задачу реализовывали

В рамках парного программирования были реализованы:
- Добавлена валидация входных данных REST-контроллеров (@Valid)
- Добавлен @NamedEntityGraph для оптимизации запросов (решение проблемы N+1)
- Написаны unit-тесты для сервиса и интеграционные тесты для репозиториев
- ReviewService (Система отзывов)
- Реализована модель Review с связями ManyToOne (Book, User)
- Создана логика автоматического пересчета рейтинга книги при добавлении/удалении отзыва
- Добавлена валидация: оценка от 1 до 5, комментарий опционально


## 3. Какой стиль показался более приемлемым? Почему?

Наиболее эффективным оказался стиль «Пинг-понг».

Причины:
- Высокое качество кода: Написание теста до реализации заставляло тщательно продумывать контракты методов и граничные случаи (например, что делать при удалении автора, у которого есть книги).
- Раннее обнаружение ошибок: Баги выявлялись на этапе написания тестов, а не при ручном тестировании через Postman.
- Вовлеченность обоих разработчиков: Нельзя было "выключиться" — каждый активно участвовал либо в написании теста, либо в реализации.
- Документирование через тесты: Тесты стали живой документацией, показывающей, как должен работать код.

Стиль «Ведущий-ведомый» хорошо показал себя при:
- Изучении специфики JPA (каскады, стратегии загрузки)
- Настройке сложных запросов (JPQL с JOIN FETCH)
- Понимании архитектуры проекта

Но для основной разработки бизнес-логики "пинг-понг" оказался продуктивнее.

## 4. Что получилось? Положительные впечатления
   
Что удалось:

1. Качество кода:
- Достигнуто покрытие тестами >80% для критических компонентов
- Отсутствие проблемы N+1 запросов благодаря @NamedEntityGraph
- Корректная обработка каскадного удаления (методы @PreRemove в Author и Category)

2. Взаимодействие в команде:
- Произошел активный обмен знаниями: один разработчик лучше знал React, второй — Spring Boot
- Сформировалось коллективное владение кодом — оба разработчика понимают и бэкенд, и фронтенд
- Улучшилась коммуникация: вопросы решались мгновенно, без долгих обсуждений в чате

3. Технические достижения:
- Успешно реализована сложная логика пересчета рейтинга при добавлении/удалении отзывов
- Настроены оптимальные стратегии загрузки данных для производительности
- Реализована валидация на всех уровнях (фронтенд, контроллеры, сервисы)

Положительные впечатления:
- Работа в паре мотивировала не отвлекаться на посторонние дела
- Моментальная обратная связь помогала избегать тупиковых решений
- Было интересно наблюдать за подходом напарника к решению задач — перенял несколько полезных практик (горячие клавиши IntelliJ, шаблоны тестов, подходы к отладке)
- Обсуждение архитектурных решений в реальном времени приводило к более качественным компромиссам

## 5. Что не получилось? Как можно это поправить?

   Проблемы и их решения:
   
1. Перенастройка окружения при смене ролей

   Проблема: При передаче клавиатуры новый "ведущий" тратил время на настройку шрифта, открытие нужных вкладок, привыкание к чужой IDE

   Решение: Договорились использовать общие настройки форматирования кода и настроили синхронизацию конфигурации IDE через Settings Repository

2. Стиль "Ведущий-ведомый" иногда превращался в "Наблюдай за Мастером"

   Проблема: Более опытный разработчик иногда начинал диктовать решение, не давая напарнику подумать самостоятельно

   Решение: Сознательно следили за этим и чаще менялись ролями, даже если второй разработчик был менее уверен. Ввели правило: "водитель" всегда пишет код сам, даже если медленно

3. Дискуссии о стиле кода

   Проблема: Возникали споры о форматировании (пробелы vs табуляция, расположение аннотаций JPA)

   Решение: Подключили Checkstyle и EditorConfig, чтобы автоматически приводить код к единому стандарту при сохранении

4. Усталость при длительных сессиях

   Проблема: После 3 часов непрерывной парной работы концентрация падала, начинали раздражать мелкие ошибки напарника

   Решение: Ввели технику Pomodoro (50 минут работы / 10 минут отдыха) и договорились не работать в паре более 4 часов в день

5. Сложность параллельной работы над разными компонентами

   Проблема: Иногда хотелось разделиться: один пишет тесты, другой — реализацию, но физически это сложно за одним компьютером

   Решение: Использовали IntelliJ Code With Me для удаленной парной работы, что позволило каждому работать в своей IDE, но видеть код напарника

## 6. Будете ли использовать ПП для других задач? Каких?
  
Да, планируем использовать парное программирование для:

1. Сложные бизнес-задачи:
- Реализация поиска книг с фильтрацией по нескольким критериям (автор, жанр, год, рейтинг)
- Добавление пагинации и сортировки на бэкенде и фронтенде
- Интеграция с внешними API (например, Google Books API для импорта)

2. Рефакторинг критического кода:
- Переход на ролевую модель (добавление прав ADMIN/LIBRARIAN)
- Оптимизация производительности (кэширование через Redis)
- Миграция на новую версию Spring Boot или React

3. Онбординг новых разработчиков:
- Парное программирование — лучший способ ввести нового члена команды в проект, показать архитектуру и договоренности

4. Расследование сложных багов:
- Особенно тех, которые трудно воспроизвести или которые затрагивают несколько компонентов (например, рассинхронизация данных между БД и кэшем)

5. Написание сложных тестов:
- Интеграционные тесты с несколькими сущностями (проверка каскадных операций)
- Тесты производительности

Не будем использовать для:
- Рутинных задач (написание простых CRUD-методов, однотипных DTO)
- Задач, требующих длительной фоновой работы (например, оптимизация запросов, требующая часового анализа планов выполнения)
- Ситуаций, когда оба разработчика устали и продуктивность падает (лучше поработать индивидуально или отдохнуть)

## Выводы

Парное программирование показало себя эффективным инструментом для разработки ключевых компонентов онлайн-библиотеки. Несмотря на небольшое замедление на начальном этапе (примерно 15-20% по сравнению с индивидуальной работой), качество кода и скорость обнаружения ошибок значительно выросли.

Особенно полезным оказался стиль "пинг-понг" для обеспечения высокого покрытия тестами и чистоты архитектуры. Он заставлял заранее продумывать контракты методов и граничные случаи, что в итоге сократило время на отладку.

В дальнейшем планируем использовать парное программирование точечно — для наиболее сложных и критичных задач, комбинируя его с индивидуальной работой над рутинными компонентами. Такой гибридный подход позволит сохранить высокое качество ключевых частей системы без потери общей скорости разработки.
